# S3

## Classes de Armazenamento (Storage Classes)

- **S3 Standard (padrão)**:
    - Os objetos são armazenados em pelo menos 3 AZs
    - Fornece onze noves de disponibilidade (nota: projetado para onze noves de durabilidade)
    - A replicação utiliza verificações de arquivo MD5 junto com CRCs para detectar problemas nos objetos
    - Quando os objetos são armazenados no S3 usando a API, uma resposta HTTP 200 OK é retornada
    - Faturamento: 
        - GB/mês de dados armazenados no S3
        - Cobrança por GB para transferência de saída (a de entrada é gratuita)
        - Preço por 1.000 requisições
        - Sem taxa de recuperação específica, sem duração mínima, sem tamanho mínimo
    - O S3 Standard torna os dados acessíveis imediatamente, podendo ser usado para hospedagem de sites estáticos
    - Deve ser usado para dados acessados com frequência
- **S3 Standard-IA (Acesso Infrequente)**:
    - Compartilha a maioria das características do S3 Standard: os objetos são replicados em 3 AZs, a durabilidade é a mesma, a disponibilidade é a mesma, a latência do primeiro byte é a mesma e os objetos podem ser tornados públicos
    - Faturamento:
        - É mais econômico para o armazenamento de dados
        - A taxa de transferência de dados é a mesma do S3 Standard
        - Taxa de recuperação: para cada GB de dados recuperado há uma taxa, o que pode aumentar o custo total se o acesso aos dados for frequente
        - Cobrança de duração mínima: será cobrado um mínimo de 30 dias, com capacidade mínima por objeto de 128 KB (objetos menores serão cobrados como se tivessem 128 KB)
    - Deve ser usado para dados de longa vida útil cujo acesso seja infrequente
- **S3 One Zone-IA**:
    - Semelhante ao S3 Standard-IA, mas mais barato. Também é mais barato que o S3 Standard-IA convencional
    - Os dados armazenados nesta classe são mantidos em apenas uma única AZ (Zona de Disponibilidade) da região
    - Faturamento:
        - Semelhante ao S3 Standard-IA: taxa de duração mínima semelhante de 30 dias, faturamento semelhante para objetos menores e taxa de recuperação por GB idêntica
        - Mesmo nível de durabilidade (desde que a AZ não sofra uma falha catastrófica)
        - Os dados são replicados dentro de apenas 1 AZ
    - Como os dados não são replicados entre múltiplas AZs, esta classe de armazenamento não possui alta disponibilidade (HA). Deve ser usada para dados não críticos ou que possam ser facilmente reproduzidos
- **S3 Glacier Instant Retrieval**:
    - É semelhante ao S3 Standard-IA, mas com armazenamento mais barato, recuperação mais cara e períodos mínimos mais longos
    - Recomendado para dados acessados infreqüentemente (uma vez por trimestre), mas que ainda precisam ser recuperados instantaneamente
    - A cobrança de duração mínima de armazenamento é de 90 dias
- **S3 Glacier Flexible Retrieval (anteriormente conhecido apenas como S3 Glacier)**:
    - Mesma replicação de dados do S3 Standard e S3 Standard-IA
    - Mesmas características de durabilidade
    - O custo de armazenamento é cerca de 1/6 do S3 Standard
    - Os objetos do S3 armazenados no Glacier devem ser considerados dados frios (não devem ser acessados com frequência)
    - Os objetos na classe Glacier são apenas ponteiros para os objetos reais e não podem ser tornados públicos diretamente
    - Para recuperá-los, precisamos realizar um processo de solicitação de recuperação:
        - Um trabalho (job) que deve ser executado para obter acesso aos objetos
        - Os processos de recuperação são cobrados
        - Quando os objetos são recuperados do Glacier, eles são armazenados temporariamente no Standard-IA e removidos após um tempo. Também podemos recuperá-los permanentemente
    - Tipos de trabalhos de recuperação:
        - **Expedited (Expedita)**: os objetos são recuperados em 1-5 minutos; este processo de recuperação é o mais caro
        - **Standard (Padrão)**: os dados ficam acessíveis em 3-5 horas
        - **Bulk (Em lote)**: os dados ficam acessíveis em 5-12 horas a um custo mais baixo
    - O Glacier possui um tamanho mínimo faturável de 40 KB e uma duração mínima de armazenamento de 90 dias
    - O Glacier deve ser usado para arquivamento de dados (acesso anual), onde os dados podem ser recuperados em minutos ou horas
- **S3 Glacier Deep Archive**:
    - O Deep Archive representa dados em um estado totalmente congelado
    - Possui um tamanho de dados mínimo faturável de 40 KB e uma duração mínima de armazenamento de 180 dias
    - Os objetos não podem ser tornados públicos; o acesso aos dados é semelhante à classe Glacier padrão
    - Os trabalhos de restauração são mais longos:
        - **Standard (Padrão)**: até 12 horas
        - **Bulk (Em lote)**: até 48 hours
    - Deve ser usado para arquivamento de dados que são raramente acessados
- **S3 Intelligent-Tiering**:
    - É uma classe de armazenamento que contém 5 camadas (tiers) de armazenamento diferentes
    - Os objetos acessados com frequência são armazenados na camada de Acesso Frequente, os menos acessados na camada de Acesso Infrequente. Objetos acessados muito raramente serão movidos para as camadas de Archive ou Deep Archive
    - Não precisamos nos preocupar em mover os objetos entre as camadas; isso é feito automaticamente pela classe de armazenamento
    - A camada inteligente pode ser configurada; o arquivamento automático de dados é opcional e pode ser ativado ou desativado
    - Não há custo de recuperação ao mover dados entre as camadas frequentes e infrequentes; seremos cobrados com base em uma taxa de automação por 1.000 objetos
    - O S3 Intelligent-Tiering é recomendado para padrões de acesso a dados desconhecidos ou incertos

## Configuração de Ciclo de Vida do S3 (S3 Lifecycle Configuration)

- Podemos criar regras de ciclo de vida nos buckets do S3 para mover objetos entre as camadas ou expirar os dados automaticamente
- Uma configuração de ciclo de vida é um conjunto de regras aplicadas a um bucket ou a um grupo de objetos dentro de um bucket
- As regras consistem em ações:
    - Ações de transição: movem objetos de uma camada para outra após um determinado período de tempo
    - Ações de expiração: excluem objetos ou versões antigas de objetos
- Os objetos não podem ser movidos com base em quantas vezes são acessados por meio de regras tradicionais; isso é exclusividade do Intelligent-Tiering. O ciclo de vida move os objetos com base no tempo decorrido
- Ao mover objetos de uma camada para outra, podemos economizar custos; a expiração de objetos também ajuda a reduzir despesas
- Transições entre camadas:
    ![Transição entre camadas](images/S3StorageClassesLifecycleConfiguration.png)
- Considerações:
    - Arquivos do One Zone-IA podem transicionar para o Glacier Flexible ou Deep Archive, mas NÃO para o Glacier Instant Retrieval
    - Objetos menores custam mais proporcionalmente no Standard-IA, One Zone-IA, etc.
    - Um objeto precisa permanecer por pelo menos 30 dias na camada Standard antes de poder ser movido para as camadas de acesso infrequente por ciclo de vida (embora os objetos possam ser enviados diretamente para o IA no upload manual)
    - Uma única regra não pode mover objetos instantaneamente do Standard-IA para o Glacier se não cumpriu os prazos mínimos. Os objetos precisam respeitar as janelas de tempo. Para superar isso, podemos definir regras ou filtros distintos

## Replicação do S3 (S3 Replication)

- O S3 suporta 2 tipos de replicação:
    - Replicação entre regiões (CRR - Cross-Region Replication)
    - Replicação na mesma região (SRR - Same-Region Replication)
- Ambos os tipos de replicação oferecem suporte para replicação na mesma conta ou entre contas diferentes (cross-account)
- Se configurarmos a replicação entre contas, precisamos definir uma política no bucket de destino para permitir a replicação vinda da conta de origem
- Podemos replicar todos os objetos de um bucket ou criar regras para um subconjunto específico. Podemos filtrar os objetos a serem replicados com base em prefixos, tags ou ambos
- Podemos especificar qual classe de armazenamento usar no bucket de destino (por padrão: usa a mesma classe do objeto de origem)
- Também podemos definir a propriedade dos objetos no bucket de destino. Por padrão, será o mesmo proprietário do bucket de origem
- Controle de Tempo de Replicação (RTC - Replication Time Control): se ativado, garante a replicação dos objetos em até 15 minutos
- Considerações sobre replicação:
    - Por padrão, a replicação não é retroativa: apenas os novos objetos criados após a ativação da regra serão replicados
    - O versionamento (Versioning) precisa estar ativado tanto no bucket de origem quanto no de destino
    - A replicação em lote (Batch Replication) pode ser usada para replicar objetos existentes. Ela precisa ser configurada especificamente, caso contrário, o histórico não será movido
    - A replicação por padrão é unidirecional (origem => destino). Existe a opção de configurar a replicação bidirecional, mas isso exige configuração explícita
    - A replicação é capaz de lidar com objetos criptografados com SSE-S3 e SSE-KMS (com configuração adicional). O SSE-C (chaves gerenciadas pelo cliente) também passou a ser suportado recentemente
    - A replicação exige que o proprietário do bucket de origem tenha permissões explicitas sobre os objetos que serão replicados
    - Eventos de sistema não serão replicados, apenas eventos gerados pelo usuário
    - Quaisquer objetos que já estejam na classe Glacier e Glacier Deep Archive não serão replicados por regras padrão
    - Por padrão, as exclusões (deletions) não são replicadas. Podemos ativar a replicação de eventos de exclusão nas configurações da regra
- Casos de uso de replicação:
    - SRR:
        - Agregação de logs
        - Sincronização entre ambientes de Produção (PROD) e Teste
        - Resiliência com critérios estritos de soberania de dados
    - CRR:
        - Melhorias de resiliência global (DR)
        - Redução de latência aproximando os dados do usuário final

## Criptografia do S3 (S3 Encryption)

- Os buckets em si não são criptografados; os objetos dentro dos buckets é que são criptografados
- Tipos de criptografia em repouso (at rest):
    - Criptografia no lado do cliente (Client-Side): os dados são criptografados antes de saírem do cliente
    - Criptografia no lado do servidor (Server-Side): os dados são criptografados no lado do servidor, sendo enviados em texto puro (plain-text) a partir do cliente
- Ambos os tipos utilizam criptografia em trânsito (HTTPS) para a comunicação segura
- A criptografia no lado do servidor é mandatória; não podemos armazenar dados no S3 sem que estejam criptografados
- Existem 3 tipos de criptografia no lado do servidor suportados:
    - **SSE-C**: criptografia no lado do servidor com chaves fornecidas pelo cliente (customer-provided keys)
        - O cliente é responsável por gerenciar as chaves; o S3 cuida do processo de criptografia e decodificação
        - Quando um objeto é enviado para o S3, precisamos fornecer a chave utilizada
        - O objeto será criptografado por essa chave, e um hash criptográfico é gerado e armazenado para validar a chave depois
        - A chave de texto puro é descartada da memória do S3 assim que a criptografia termina
        - Em caso de recuperação do objeto, precisamos fornecer exatamente a mesma chave novamente
    - **SSE-S3** (padrão): criptografia no lado do servidor com chaves gerenciadas pelo Amazon S3
        - A AWS lida tanto com a criptografia/decodificação quanto com o gerenciamento das chaves
        - Ao usar este método, o S3 cria uma chave mestra para o processo de criptografia (gerenciado inteiramente pelo S3)
        - Quando um objeto é carregado, uma chave exclusiva é usada para a criptografia. Após o processo, essa chave exclusiva é criptografada com a chave mestra e a chave original em texto puro é descartada. Tanto a chave criptografada quanto o objeto são armazenados juntos
        - Para a maioria das situações, este é o tipo padrão. Utiliza o algoritmo AES-256 e o ciclo de vida das chaves é cuidado pelo S3
    - **SSE-KMS**: criptografia no lado do servidor com chaves gerenciadas no AWS Key Management Service (KMS)
        - Semelhante ao SSE-S3, mas neste método o KMS gerencia e protege as chaves utilizadas
        - Quando um objeto é carregado pela primeira vez, o S3 se comunica com o KMS e utiliza uma chave mestra do cliente (CMK - Customer Master Key)
        - Quando novos objetos são enviados, a AWS usa a CMK para gerar chaves de criptografia de dados individuais (DEKs - data encryption keys). A chave de criptografia de dados será armazenada junto com o objeto em formato criptografado
        - Não precisamos usar a CMK padrão fornecida pela AWS; podemos criar e usar nossa própria chave customizada no KMS, controlando as permissões e políticas de rotação
        - O SSE-KMS fornece separação de funções (role separation):
            - Podemos especificar quem tem acesso à chave no KMS
            - Administradores podem gerenciar os buckets do S3, mas podem não ter permissão para decodificar os dados contidos neles se não possuírem acesso à chave KMS
- Criptografia padrão do bucket (Default Bucket Encryption):
    - Quando um objeto é enviado, podemos especificar qual criptografia usar adicionando um cabeçalho à requisição: `x-amz-server-side-encryption`
    - Valores para o cabeçalho:
        - Para usar SSE-S3: `AES256`
        - Para usar SSE-KMS: `aws:kms`
    - Todos os buckets do Amazon S3 possuem criptografia configurada por padrão, e todos os novos objetos enviados para um bucket do S3 são criptografados automaticamente em repouso
    - A criptografia com chaves gerenciadas pelo Amazon S3 (SSE-S3) é a configuração padrão para todos os buckets, podendo ser sobrescrita em uma requisição PUT com o cabeçalho correspondente

## Chaves de Bucket do S3 (S3 Bucket Keys)

- Cada objeto em um bucket utiliza uma chave de criptografia de dados exclusiva (DEK - data-encryption key)
- A AWS usa a chave KMS do bucket para gerar essa chave de criptografia de dados
- Chamadas frequentes ao KMS possuem um custo associado e estão sujeitas a limites de taxa (throttling): 5.500 / 10.000 / 50.000 requisições PUT/segundo dependendo da região
- S3 Bucket Keys:
    - Uma chave de bucket com tempo limitado é usada para gerar as DEKs localmente dentro do próprio S3
    - O KMS gera uma chave de bucket e a entrega ao S3 para que ele crie as DEKs de cada upload, reduzindo drasticamente a carga de requisições enviadas ao KMS
    - Reduz o número de chamadas de API do KMS => reduz custos e aumenta a escalabilidade
- A ativação de chaves de bucket não é retroativa; ela afetará apenas os novos objetos criados após a ativação do recurso
- Itens para lembrar após ativar as chaves de bucket:
    - Os logs de eventos do KMS no CloudTrail mostrarão o ARN do bucket em vez do ARN do objeto individual
    - Menos eventos do KMS serão registrados no CloudTrail (já que o trabalho foi delegado ao S3)
    - Funcionam perfeitamente com SRR e CRR; as configurações de criptografia dos objetos são mantidas
    - Se você replicar dados em texto puro para um bucket que usa bucket keys, o objeto será criptografado no destino; isso pode resultar em alterações no ETag do objeto

## URLs Pré-assinadas do S3 (S3 Presigned URLs)

- É uma maneira de conceder a outras pessoas acesso aos nossos buckets usando nossas próprias credenciais por tempo limitado
- Um administrador ou aplicação pode gerar uma URL pré-assinada para um objeto específico usando suas credenciais. Essa URL terá uma data/hora de expiração definida
- A URL pré-assinada pode ser fornecida a usuários não autenticados para que eles acessem o recurso de forma segura
- O usuário interagirá com o S3 usando a URL pré-assinada exatamente com os privilégios da identidade que a gerou
- Podem ser usadas tanto para downloads quanto para uploads de arquivos
- São excelentes para fornecer acesso direto a arquivos privados para os usuários de uma aplicação, reduzindo a carga de tráfego do servidor backend. Essa abordagem requer que a aplicação possua as permissões necessárias para gerar as URLs pré-assinadas
- Considerações sobre URLs pré-assinadas:
    - É possível gerar uma URL pré-assinada para objetos aos quais você não tem acesso no momento da geração, mas ela falhará ao ser usada
    - Ao utilizar a URL, as permissões são avaliadas no exato momento do acesso ao objeto (se a identidade que gerou a URL tiver suas permissões revogadas nesse intervalo, a URL pré-assinada deixará de funcionar imediatamente)
    - Deve-se evitar gerar URLs pré-assinadas baseadas em credenciais temporárias (como a assunção de uma IAM Role). Quando as credenciais temporárias expirarem, a URL pré-assinada também parará de funcionar. Recomenda-se o uso de identidades de longo prazo, como um IAM User técnico, se a URL precisar durar mais tempo

## S3 Select e Glacier Select

- São maneiras de recuperar partes específicas de objetos em vez de baixar o arquivo inteiro
- O S3 pode armazenar objetos imensos (de até 5 TB)
- Baixar um objeto gigante consome tempo, processamento e capacidade de transferência de rede
- O S3 Select e o Glacier Select fornecem a capacidade de acessar partes dos objetos usando declarações semelhantes a SQL para filtrar e selecionar apenas as linhas ou campos necessários
- Ambos oferecem suporte aos seguintes formatos de arquivo: CSV, JSON, Parquet, além de compressão BZIP2 para CSV e JSON

## Pontos de Acesso do S3 (S3 Access Points)

- Melhoram a governança e o gerenciamento de acesso quando os buckets são compartilhados por times diferentes ou contêm dados para uma grande quantidade de funções distintas
- Os Access Points simplificam o processo de gerenciamento de permissões em buckets grandes
- Em vez de gerenciar uma única política de bucket massiva e complexa, podemos criar múltiplos pontos de acesso, cada um com sua própria política de acesso dedicada
- Cada ponto de acesso pode ser limitado para permitir conexões apenas de redes específicas (como dentro de uma VPC) e possuir controles de rede distintos
- Cada ponto de acesso possui seu próprio endereço de endpoint exclusivo
- Podemos criar pontos de acesso pelo console ou pela CLI usando: `aws s3control create-access-point --name <nome> --account-id <account-id> --bucket <nome-do-bucket>`
- Qualquer permissão definida no ponto de acesso precisa ser permitida também na política do bucket subjacente. Podemos fazer delegação, definindo permissões amplas na política do bucket e regras granulares na política do ponto de acesso

## Bloqueio de Acesso Público do S3 (S3 Block Public Access)

- O recurso Amazon S3 Block Public Access fornece configurações para pontos de acesso, buckets e contas inteiras para ajudar a gerenciar e restringir o acesso público aos recursos do Amazon S3
- As configurações que podemos ajustar com este recurso são:
    - **IgnorePublicAcls**: impede que novas ACLs públicas sejam criadas ou que ACLs existentes sejam modificadas para conceder acesso público. Sozinho, ele não afeta o funcionamento de ACLs públicas que já existiam
    - **BlockPublicAcls**: faz com que o S3 ignore quaisquer ACLs públicas existentes que concedam acesso. Não impede que elas sejam criadas, mas anula completamente seus efeitos práticos
    - **BlockPublicPolicy**: impede que uma política de bucket que contenha ações públicas seja criada ou modificada no bucket do S3. O bucket ainda manterá e executará políticas públicas criadas antes da ativação dessa regra
    - **RestrictPublicBuckets**: impede que serviços de terceiros fora da AWS ou usuários não autorizados acessem publicamente os objetos do bucket, restringindo o acesso apenas a identidades autorizadas e proprietárias

## Opções de Economia de Custo do S3 (S3 Cost Saving Options)

- S3 Select e Glacier Select: economizam custos de rede e CPU ao recuperar apenas os dados estritamente necessários
- Regras de Ciclo de Vida do S3: transicionam objetos automaticamente para camadas mais baratas à medida que os dados envelhecem
- Compactar/comprimir os objetos antes do upload para economizar espaço de armazenamento
- S3 Requester Pays (O Solicitante Paga):
    - Em geral, os proprietários de buckets pagam por todos os custos de armazenamento e transferência de dados associados ao seu bucket
    - Com o recurso Requester Pays ativado, o usuário que faz a solicitação de download (o solicitante) passa a pagar pelo custo da requisição e pela transferência de saída dos dados baixados do bucket
    - O proprietário do bucket continua pagando pelo custo fixo de armazenamento dos dados
    - Extremamente útil quando queremos compartilhar grandes conjuntos de dados (datasets) com outras contas ou parceiros externos
    - Exige a configuração de uma política de bucket adequada
    - Se uma IAM Role for assumida pelo solicitante, a conta proprietária dessa role pagará pela requisição!

## S3 Object Lock (Bloqueio de Objetos)

- O Object Lock pode ser habilitado facilmente em buckets novos no momento da criação. Para buckets que já existem, habilitar o Object Lock exige entrar em contato com o suporte da AWS
- O versionamento (Versioning) é ativado obrigatoriamente e de forma automática quando o Object Lock é habilitado
- O Object Lock não pode ser desativado e o versionamento não pode ser suspenso enquanto o recurso estiver ativo no bucket
- O Object Lock utiliza uma arquitetura WORM (Write-Once-Read-Many): uma vez que o dado é escrito, ele não pode ser modificado ou excluído. Versões individuais dos objetos são travadas
- Existem 2 maneiras pelas quais o S3 gerencia a retenção de objetos travados:
    - Período de Retenção (Retention Period)
    - Retenção Legal (Legal Hold)
- Versões de objetos podem ter ambos os modos (período de retenção e retenção legal) ativados simultaneamente, apenas um deles ou nenhum

### Período de Retenção (Retention Period)

- Ao ativar um período de retenção em um objeto, especificamos a quantidade de dias ou anos em que a trava permanecerá ativa
- O bloqueio expirará automaticamente após o término do período definido
- Existem 2 modos de período de retenção:
    - **Modo de Conformidade (Compliance mode)**: 
        - O objeto bloqueado não pode ser alterado, excluído ou sobrescrito por ninguém. O período de retenção não pode ser reduzido e o modo de retenção não pode ser alterado, nem mesmo pelo usuário raiz (root user) da conta AWS
        - Deve ser usado para conformidade regulatória estrita e auditorias judiciais
    - **Modo de Governança (Governance mode)**:
        - Os objetos não podem ser alterados, excluídos ou sobrescritos pela maioria dos usuários, mas permissões especiais podem ser concedidas a identidades específicas para permitir que alterem o bloqueio ou excluam o arquivo
        - Essas identidades precisam possuir explicitamente a permissão `s3:BypassGovernanceRetention`
        - O bloqueio de governança pode ser contornado enviando o cabeçalho `x-amz-bypass-governance-retention:true` na requisição (esse cabeçalho é enviado por padrão ao usar a interface do console)

### Retenção Legal (Legal Hold)

- Não definimos um período de tempo ou data de término para este tipo de retenção; o Legal Hold funciona simplesmente como uma chave liga/desliga (on/off) para versões específicas de um objeto
- Não podemos excluir ou sobrescrever um objeto enquanto o Legal Hold estiver ativado (`on`)
- Uma permissão explícita é exigida para adicionar ou remover o status de Legal Hold em um objeto: `s3:PutObjectLegalHold`
- É ideal para evitar remoções acidentais ou para congelar dados durante investigações em andamento

## S3 Transfer Acceleration

- Usado para acelerar o upload e transferência de arquivos para o S3 através de longas distâncias geográficas entre o cliente e o bucket de destino
- Utiliza a infraestrutura de redes globais e as localidades de borda (Edge Locations) distribuídas globalmente do Amazon CloudFront
- Cenários ideais para o uso do Transfer Acceleration:
    - Uploads vindos de usuários espalhados por todo o mundo para um bucket centralizado
    - Transferência regular de gigabytes a terabytes de dados através de continentes
    - Quando o cliente não consegue utilizar toda a sua banda de internet disponível ao fazer upload direto para os endpoints padrão do Amazon S3
- Para utilizá-lo, o recurso deve ser ativado nas configurações do bucket. Após a ativação, pode levar até 20 minutos para que a URL acelerada comece a operar em velocidade máxima

## S3 Object Lambda

- Com o Amazon S3 Object Lambda, podemos injetar nosso próprio código customizado nas requisições `GET`, `LIST` e `HEAD` do S3 para modificar, filtrar e processar os dados em tempo real antes de serem retornados para a aplicação chamadora
- O S3 Object Lambda utiliza funções do AWS Lambda para processar automaticamente a saída das requisições padrão do S3
- Após configurar a função Lambda, nós a vinculamos a um endpoint de serviço do S3 Object Lambda, conhecido como *Object Lambda Access Point*
- O Object Lambda Access Point utiliza um ponto de acesso padrão do S3 por trás
- Quando enviamos uma requisição para o Object Lambda Access Point, o Amazon S3 intercepta a chamada e executa a função Lambda automaticamente, entregando o dado transformado (ex: mascarando dados sensíveis, alterando formatos de imagem, etc.)

## Hospedagem de Site Estático no S3 (Hosting Static Site on S3)

- Podemos hospedar sites estáticos inteiros diretamente dentro de um bucket do S3
- Para hospedar um site estático, precisamos ativar o recurso de hospedagem de site estático (static website hosting) nas propriedades do bucket, configurar o documento de índice (ex: `index.html`) e ajustar as permissões
- Também devemos tornar o conteúdo do bucket público:
    - Desativar as configurações de Bloqueio de Acesso Público (Block Public Access) do bucket
    - Adicionar uma política de bucket (bucket policy) que conceda permissão de leitura pública (`s3:GetObject`) em todos os objetos contidos nele
- Atenção: Os endpoints nativos de website do Amazon S3 suportam apenas HTTP e não oferecem suporte nativo a HTTPS! Se você precisar usar criptografia e HTTPS no seu domínio, deverá utilizar o Amazon CloudFront na frente do bucket do S3 para servir o site de forma segura

## Storage Classes

- **S3 Standards (default)**:
    - The objects are stored in at least 3 AZs
    - Provides eleven nines of availability
    - The replication is using MD5 file checks together with CRCs to detect object issues
    - When objects are stored in S3 using the API, a HTTP 200 OK response is provided
    - Billing: 
        - GB/month of data stored in S3
        - A dollar for GB charge transfer out (in is free)
        - Price per 1000 requests
        - No specific retrieval fee, no minimum duration, no minimum size
    - S3 standard makes data accessible immediately, can be used for static website hosting
    - Should be used for data frequently accessed
- **S3 Standard-IA**:
    - Shares most of the characteristics of S3 standard: objects are replicated in 3 AZs, durability is the same, availability is the same, first byte latency is the same, objects can be made publicly available
    - Billing:
        - It is more cost effective for storing data
        - Data transfer fee is the same as S3 standard
        - Retrieval fee: for every GB of data there is a retrieval fee, overall cost may increase with frequent data access
        - Minimum duration charge: we will be billed for a minimum of 30 days, minimum capacity of the objects being 128KB (smaller objects will be billed as being 128 KB)
        - Should be used for long lived data where data access is infrequent
- **S3 One Zone-IA**:
    - Similar to S3 standard, but cheaper. Also cheaper than S3 standard IA
    - Data stored using this class is only stored in one region
    - Billing:
        - Similar to S3 standard IA: similar minimum duration fee of 30 days, similar billing for smaller objects and also similar retrieval fee per GB
        - Same level of durability (if the AZ does not fail)
        - Data is replicated inside one AZ
    - Since data is not replicated between AZs, this storage class is not HA. It should be used for non-critical data or for data that can be reproduced easily
- **S3 Glacier Instant Retrieval**:
    - It like S3 Standard-IA, but with cheaper storage, more expensive retrieval, longer minimums
    - Recommended for data that is infrequently accessed (once per quarter), but it still needs to be retrieved instantly
    - Minimum storage duration charge is 90 days
- **S3 Glacier Flexible Retrieval (formerly knowns as S3 Glacier)**:
    - Same data replication as S3 standard and S3 standard IA
    - Same durability characteristics
    - Storage cost is about 1/6 of S3 standard
    - S3 objects stored in Glacier should be considered cold objects (should not be accessed frequently)
    - Objects in Glacier class are just pointers to real objects and they can not be made public
    - In order to retrieve them, we have to perform a retrieval process:
        - A job that needs to be done to get access to objects
        - Retrievals processes are billed
        - When objects are retrieved for Glacier, they are temporarily stored in standard IA and they are removed after a while. We can retrieve them permanently as well
    - Retrieval job types:
        - **Expedited**: objects are retrieved in 1-5 minutes, retrieval process being the most expensive
        - **Standard**: data is accessible at 3-5 hours
        - **Bulk**: data is accessible at 5-12 hours at lower cost
    - Glacier has a 40KB minimum billable size and a 90 days minimum duration for storage
    - Glacier should be used for data archival (yearly access), where data can be retrieved in minutes to hours
- **S3 Glacier Deep Archive**:
    - Deep Archive represents data in a frozen state
    - Has a 40KB minimum billable data size and a 180 days minimum duration for data storage
    - Objects can not be made publicly available, data access is similar to standard Glacier class
    - Restore jobs are longer:
        - **Standard**: up to 12 hours
        - **Bulk**: up to 48 hours
    - Should be used for archival which is very rarely accessed
- **S3 Intelligent-Tiering**:
    - It is a storage class containing 5 different tiering a storage
    - Objects that are access frequently are stored in the Frequent Access tier, less frequently accessed objects are stored in the Infrequent Access tier. Objects accessed very infrequently will be stored in either Archive or Deep Archive tier
    - We don't have to worry for moving objects over tier, this is done by the storage class automatically
    - Intelligent tier can be configured, archiving data is optional and can be enabled/disabled
    - There no retrieval cost for moving data between frequent and infrequent tiers, we will be billed based on the automation cost per 1000 objects
    - S3 Intelligent-Tiering is recommended for unknown or uncertain data access usage

## S3 Lifecycle Configuration

- We can create lifecycle rules on S3 buckets which can move objects between tiers or expire objects automatically
- A lifecycle configuration is a set of rules applied to a bucket or a group of objects in a bucket
- Rules consist of actions:
    - Transition actions: move objects from one tier to another after a certain time
    - Expiration actions: delete objects or versions of objects
- Objects can not be moved based on how much they are accessed, this can be done by the intelligent tiering. We can move objects based on time passed
- By moving objects from one tier to another we can save costs, expiring objects also will help saving costs
- Transitions between tiers:
    ![Transition between tiers](images/S3StorageClassesLifecycleConfiguration.png)
- Considerations:
    - Files from One Zone-IA can transition to Glacier Flexible, or Deep Archive, NOT into Glacier Instant retrieval
    - Smaller objects cost more in Standard-IA, One Zone-IA, etc.
    - An object needs to remain for at least 30 days in standard tier before being able to be moved to infrequent tiers (objects can be uploaded manually in infrequent tiers)
    - A single rule can not move objects instantly from standard IA to infrequent tiers and then to Glacier tiers. Objects have to stay for at least 30 days in infrequent tiers before being able to be moved by one rule only. In order ot overcome this, we can define 2 different rules

## S3 Replication

- 2 types of replication are supported by S3:
    - Cross-Region Replication (CRR)
    - Same-Region Replication (SRR)
- Both types of replication support same account replication and cross-account replication
- If we configure cross-account replication, we have to define a policy on the destination account to allow replication from the source account
- We can create replicate all objects from a bucket or we can create rules for a subset of objects. We can filter objects to replicate based on prefix or tags or both
- We can specify which storage class to use for an object in the destination bucket (default: use the same class)
- We can also define the ownership of the objects in the destination bucket. By default it will be the same as the owner in the source bucket
- Replication Time Control (RTC): if enabled ensures a 15 minutes replication of objects
- Replication consideration:
    - By default replication is not retroactive: only newer objects are replicated after the replication is enabled
    - Versioning needs to be enabled for both source and destination buckets
    - Batch replication can be used to replicate existing objects. It needs to be specifically configured. If it is not, replication wont be retroactive
    - Replication by default one-way only, source => destination. There is an option to use bi-directional replication, but this has to be configured
    - Replication is capable of handling objects encrypted with SSE-S3 and SSE-KMS (with extra configuration). SSE-C (customer managed keys) is also supported, historically it was incompatible
    - Replication requires for the owner of source bucket needs permissions on the objects which will be replicated
    - System events will not be replicated, only user events
    - Any objects in the Glacier and Glacier Deep Archive will not be replicated
    - By default, deletion are not replicated. We can enable replication for deletion events
- Replication use cases:
    - SRR:
        - Log aggregation
        - PROD and Test sync
        - Resilience with strict sovereignty
    - CRR
        - Global resilience improvements
        - Latency reduction

## S3 Encryption

- Buckets aren't encrypted, objects inside buckets are encrypted
- Encryption at rest types:
    - Client-Side encryption: data is encrypted before it leaves the client
    - Server-Side encryption: data is encrypted at the server side, it is sent on plain-text format from the client
- Both encryption types use encryption in-transit for communication
- Server-side encryption is mandatory, we cannot store data in S3 without being encrypted
- There are 3 types of server-side encryption supported:
    - **SSE-C**: server-side encryption with customer-provided keys
        - Customer is responsible for managing the keys, S3 managed encryption/decryption
        - When an object is put into S3, we need to provide the key utilized
        - The object will be encrypted by the key, a hash is generated and stored for the key
        - The key will be discarded after the encryption is done
        - In case of object retrieval, we need to provide the key again
    - **SSE-S3** (default): server-side encryption with Amazon S3-managed keys
        - AWS handles both the encryption/decryption and the key management
        - When using this method, S3 creates a master key for the encryption process (handled entirely by S3)
        - When an object is uploaded an unique key is used for encryption. After the encryption, this unique key is encrypted as well with the master key and the unencrypted key is discarded. Both the key and the object are stored together
        - For most situations, this is the default type of encryption. It uses AES-256 algorithm, they key management is entirely handled bt S3
    - **SSE-KMS**: Server-side encryption with customer-managed keys stored in AWS Key Management Service (KMS)
        - Similar to SSE-S3, but for this method the KMS handles stored keys
        - When an object is uploaded for the first time, S3 will communicate with KMS and creates a customer master key (CMK). This is default master key used in the future
        - When new objects are uploaded AWS uses the CMK to generate individual keys for encryption (data encryption keys). The data encryption key will be stored along with the object in encrypted format
        - We don't have to use the default CMK provided by AWS, we can use our own CMK. We can control the permission on it and how it is regulated
        - SSE-KMS provides role separation:
            - We can specify who can access the CMK from KMS
            - Administrators can administers buckets but they may not have access to KMS keys
- Default Bucket Encryption:
    - When an object is uploaded, we can specify which server-side encryption to be used by adding a header to the request: `x-amz-server-side-encryption`
    - Values for the header:
        - To use SSE-S3: `AES256`
        - To use SSE-KMS: `aws:kms`
    - All Amazon S3 buckets have encryption configured by default, and all new objects that are uploaded to an S3 bucket are automatically encrypted at rest
    - Server-side encryption with Amazon S3 managed keys (SSE-S3) is the default encryption configuration for every bucket in Amazon S3, this can be overridden in a PUT request with `x-amz-server-side-encryption` header

## S3 Bucket Keys

- Each object in a bucket is using a uniq data-encryption key (DEK)
- AWS uses the bucket's KMS key to generate this data-encryption key
- Calls to KMS have a cost and levels where throttling occurs: 5500/10_000/50_000 PUT/sec depending on region
- Bucket keys:
    - A time limited bucket key is used to generate DEKs within S3
    - KMS generates a bucket key and gives it to S3 to use to generate DEKs for each upload, offloading the load from KMS to S3
    - Reduces the number of KMS API calls => reduces the costs/increases scalability
- Using bucket keys is not retroactive, it will only affect objects after bucket keys are enabled
- Thing to keep in mind after enabling bucket keys:
    - CloudTrail KMS event logs will show the bucket ARN instead of the object ARN
    - Fewer CloudTrail events of KMS will be in the logs (since work is offloaded to S3)
    - Bucket keys work with SRR and CRR; the object encryption settings are maintained
    - If we replicate plaintext to a bucket using bucket keys, the object is encrypted at the destination side; this can result in ETAG changes on the object

## S3 Presigned URLs

- Is a way to give other people access to our buckets using our credentials
- An IAM admin can generate a presigned URL for a specific object using his credentials. This URL will have an expiry date
- The presigned URL can be given to unauthenticated uses in order to access the object
- The user will interact with S3 using the presigned URL as if it was the person who generated the presigned URL
- Presigned URLs can be used for downloads and for uploads
- Presigned URLs can be used for giving direct access private files to an application user offloading load from the application. This approach will require a service account for the application which will generate the presigned URLs
- Presigned URL considerations:
    - We can create a presigned ULR for objects we don't have access to
    - When using the URL, the permissions match the identity which generated it. The permissions are evaluated at the moment of accessing the object (it might happen the the identity had its permissions revoked, meaning we wont have access to the object either)
    - We should not generate presigned URLs generated on temporary credentials (assuming an IAM role). When the temporary credentials are expired, the presigned URL will stop working as well. Recommended to use long-term identities such as an IAM user

## S3 Select and Glacier Select

- Are ways to retrieve parts of objects instead of entire objects
- S3 can store huge objects (up to 5 TB)
- Retrieving a huge objects will take time and consume transfer capacity
- S3/Glacier provides services to access partial objects using SQL-like statements to select parts of objects
- Both S3 Select and Glacier selects supports the following formats: CSV, JSON, Parquet, BZIP2 compression for CSV and JSON

## S3 Access Points

- Improves the manageability of objects when buckets are used for many different teams or they contain objects for a large amount of functions
- Access Points simplify the process of managing access to S3 buckets/objects
- Rather than 1 bucket (1 bucket policy) access we can create many access points with different policies
- Each access point can be limited from where it can be accessed, and each can have different network access controls
- Each access point has its own endpoint address
- We can create access point using the console or the CLI using `aws s3control create-access-point --name < name > --account-id < account-id > --bucket < bucket-name >`
- Any permission defined on the access point needs to be defined on the bucket policy as well. We can do delegation, by defining wide access permissions in the bucket policy and granular permissions on the access point policy

## S3 Block Public Access

- The Amazon S3 Block Public Access feature provides settings for access points, buckets, and accounts to help manage public access to Amazon S3 resources
- The settings we can configure with the Block Public Access Feature are:
    - **IgnorePublicAcls**: this prevents any new ACLs to be created or existing ACLs being modified which enable public access to the object. With this alone existing ACLs will not be affected
    - **BlockPublicAcls**: Any ACLs actions that exist with public access will be ignored, this does not prevent them being created but prevents their effects
    - **BlockPublicPolicy**: This prevents a bucket policy containing public actions from being created or modified on an S3 bucket, the bucket itself will still allow the existing policy
    - **RestrictPublicBuckets**: this will prevent non AWS services or authorized users (such as an IAM user or role) from being able to publicly access objects in the bucket

## S3 Cost Saving Options

- S3 Select and Glacier Select: save in network a CPU cost by retrieving ony the necessary data
- S3 Lifecycle Rules: transition objects between tiers
- Compress objects to save space
- S3 Requester Pays:
    - In general, bucket owners pay for all Amazon S3 storage and data transfer costs associated with their bucket
    - With Requester Pays buckets, the requester instead of the bucket owner pays the cost of the request and the data download from the bucket
    - The bucket owner always pays the cost of storing data
    - Helpful when we want to share large datasets with other accounts
    - Requires a bucket policy
    - If an IAM role is assumed, the owner account of that role pays for the request!

## S3 Object Lock

- Object Lock can be enabled on newly created S3 buckets. For existing ones in order to enable Object Lock we have to contact AWS support
- Versioning will be also enabled when Object Lock is enabled
- Object Lock can not be disabled, versioning can not be suspended when Object Lock is active on the bucket
- Object Lock is a Write-Once-Read-Many (WORM) architecture: when an object is written, can not be modified. Individual versions of objects are locked
- There are 2 ways S3 managed object retention:
    - Retention Period
    - Legal Hold
- Object versions can have both retention period and legal hold enabled; can have only one of those enabled or none of them
- Object Lock retentions can be individually defined on object versions, a bucket can have default Object Lock settings

### Retention Period

- When a retention period is enabled on an object, we specify the days and years for the period
- The retention period will end after the period
- There are 2 types of retention period modes:
    - **Compliance mode**: 
        - Object can not be adjusted, deleted or overwritten. The retention period can not be reduced, the retention mode can not be adjusted even by the account root user
        - Should be used for compliance reasons
    - **Governance mode**:
        - Objects can not be adjusted, deleted or overwritten, but special permissions can be added to some identities to allow for the lock setting to be adjusted
        - This identities should have the `s3:BypassGovernanceRetention` permission
        - The governance mode can be overwritten when passing `x-amz-bypass-governance-retention:true` header (header is default for console ui)

### Legal Hold

- We don't set a retention period for this type of retention, Legal Hold can be on or off for specific versions of an object
- We can't delete or overwrite an object with Legal Hold
- An extra permission is required when we want to add or remove the Legal Hold on an object: `s3:PutObjectLegalHold`
- Legal Hold can be used for preventing accidental removals

## S3 Transfer Accelerate

- Used to transfer files into S3. Enables fast, easy, and secure transfers of files over long distances between our client and an S3 bucket
- Takes advantage of the globally distributed edge locations in Amazon CloudFront
- We might want to use Transfer Acceleration on a bucket for various reasons:
    - We upload to a centralized bucket from all over the world
    - We transfer gigabytes to terabytes of data on a regular basis across continents
    - We can't use all of our available bandwidth over the internet when uploading to Amazon S3
- To use Transfer Accelerate, it must be enabled on the bucket. After we enable Transfer Acceleration on a bucket, it might take up to 20 minutes before the data transfer speed to the bucket increases

## S3 Object Lambda

- With Amazon S3 Object Lambda, we can add our own code to Amazon S3 `GET`, `LIST`, and `HEAD` requests to modify and process data as it is returned to an application
- S3 Object Lambda uses AWS Lambda functions to automatically process the output of standard S3 `GET`, `LIST`, or `HEAD` requests
- After we configure a Lambda function, we attach it to an S3 Object Lambda service endpoint, known as an *Object Lambda Access Point*
- The Object Lambda Access Point uses a standard S3 access point
- When we send a request to your Object Lambda Access Point, Amazon S3 automatically calls your Lambda function

## Hosting Static Site on S3

- We can host a static site on S3
- To host a static site in a bucket we must enable static website hosting, configure an index document, and set permissions
- We should also make a bucket content public:
    - We should turn of Block Public Access settings
    - We should attach a bucket policy which allows public read on the objects
- Amazon S3 website endpoints do not support HTTPS! If we want to use HTTPS, we can use Amazon CloudFront to serve a static website hosted on Amazon S3
